# ADR-0005: Slot bookability module

> **Status:** Accepted
> **Date:** 2026-10-30
> **Decider:** agathan (architecture lead)
> **Work item:** BQ-012 (implementation), BQ-069 (blocked-date acceptance), BQ-028 (Phase 2 package)

## Context

Availability is defined in several places that disagree ([schedule domain](../domains/schedule.md), BQ-012). Calendar and reports count every pending booking as occupied; customer selection and reschedule repeat the grace period; booking writes omit blocked-date checks (BQ-069). Replacing these queries with per-slot calls to the current `AvailabilityRules` would introduce repeated database queries rather than one shared, efficient rule.

Write paths also disagree about transaction and lock ownership. Claim-side eviction locks bookings before payments, whereas payment processing locks payments before bookings. Date closure and service/fulfillment changes have no shared synchronization with claims. `CreateBooking` evicts before validating schedule ownership and returns an error array from its transaction, so rejection can commit cleanup. Reschedule checks the source booking before the transaction and locks only the target schedule.

ADR-0004 assigns payment transitions and booking-group consequences to Payment lifecycle. Slot bookability must cooperate with that owner rather than independently expire payments or cancel group members. Required protections are INV-TEN-01, INV-BOOK-03/04/05/06 and INV-SCH-01; relevant requirements include FR-SCHEDULE-005/009, FR-BOOKING-017/018/019 and NFR-PERF-003/004.

## Options

1. **Keep separate queries and add missing checks.** Small immediate patches, but each caller still owns a different subset of the rules and locking protocol.
2. **Shared reads and a separately committed slot reservation.** Gives writes a common entry point, but introduces another reservation lifecycle and separates claiming from the actual booking/payment write.
3. **One module with shared evaluation and a claim inside the operation's transaction.** Keeps one reservation lifecycle and makes rejection atomic. A tenant-row lock coordinates all relevant writers, trading write concurrency within one tenant for simpler correctness. Chosen.

## Decision

1. **One module owns slot bookability.** Listings, calendar, reports, new bookings, walk-ins and both reschedule flows use it. It evaluates tenant/service ownership, service and fulfillment eligibility, schedule status, blocked dates, past time, occupancy and multi-slot compatibility. `BookingRules` remains the home of occupancy and the 15-minute pending grace. Quota/entitlement, pricing, source-booking lifecycle authorization and payment transitions retain their existing owners; the slot module does not duplicate them.
2. **One rule, two uses.** Read evaluation is advisory and never reserves a slot. A locked claim re-reads current database state and returns a typed acceptance or refusal. Customer and owner entry points use the same target-slot rules; callers cannot bypass them with a privilege flag. The claim does not create a separate temporary reservation entity or commit a reservation of its own.
3. **The booking/reschedule Action owns the outer transaction.** The slot module participates; acquired locks last through the actual booking/payment writes and the outer commit. Payment lifecycle still owns payment mutations and joins the same transaction when called from the operation; when invoked independently, it opens its own transaction. A rejected operation rolls back all its mutations, including stale-pending cleanup. Returning a refusal must not accidentally commit cleanup.
4. **Every relevant writer locks the tenant row first.** Before child-row locks or mutations, acquire the row for the server-resolved tenant. The protocol covers booking creation/status/cancellation/reschedule, payment outcomes and expiry, subscription changes affecting entitlement, schedule changes/blocking/unblocking, and service/staff/resource/fulfillment mutations affecting eligibility. Reload decision inputs after acquiring the lock. Global jobs process one tenant per transaction; cross-tenant bulk writes cannot bypass the protocol. Transactions stay short; gateway calls, mail and other external side effects run after the outer commit.
5. **Ownership validation precedes cleanup.** Resolve and verify every supplied identifier and every affected booking/payment group against the tenant before any mutation, including eviction. A foreign schedule or an inconsistent group is refused without changing another tenant's data. Foreign keys alone do not establish that related records have the same tenant.
6. **Stale cleanup requests a Payment lifecycle transition.** Slot bookability detects stale pending bookings using `BookingRules` and requests expiry of the complete payment group through ADR-0004's module, in the same outer transaction. It then rechecks target slots. It does not directly change payment status or cancel sibling bookings. Missing payments or inconsistent states, such as pending bookings attached to a successful payment, cause refusal and an anomaly log rather than fallback cancellation. Diagnostic logging must not depend on committing rejected business mutations or expose tokens/secrets.
7. **Closing a date prevents new claims, not existing reservations.** New bookings, walk-ins and reschedule into that date are refused. Already committed pending bookings may complete their normal payment lifecycle until their ordinary deadline; paid bookings remain valid. Closing a date does not automatically cancel them or create refunds. Closure and claims share the tenant-first protocol: whichever commits first establishes whether a reservation existed before closure.
8. **Batch data acquisition, pure evaluation.** Acquire schedules, blocked dates, service/fulfillment and occupancy data in batches, then evaluate rules over those inputs. Do not replace aggregate listings with database queries per slot. Recompute past-time and grace-period decisions on every request; cache supporting data rather than final clock-dependent availability booleans. Cached occupancy inputs must retain the information needed to evaluate grace at the current time.
9. **The module owns availability cache keys and invalidation.** Keys include the actual tenant, service, date/range and any reschedule exclusion affecting the result. After the outer commit, invalidate every affected listing/time/reschedule variant for booking, payment-group, date and service/fulfillment mutations. Claims never use cached eligibility as authority. Views, controllers and payment adapters request invalidation through the module instead of constructing keys themselves.
10. **Deadline policy is unchanged here.** Pending grace remains 15 minutes. Unifying it with payment deadlines belongs to candidate #6; this ADR does not reopen ADR-0004's late-success/refund decision or add multi-slot cancellation/reschedule capabilities.

## Consequences

- One module supplies the same rule to readers and writers. Callers no longer reconstruct availability SQL, grace conditions or cache keys.
- Writes for one tenant are serialized; different tenants remain independent. This protects correctness only if every relevant writer participates, including webhook/expiry paths, subscription jobs and fulfillment CRUD/pivot updates. A future finer-grained protocol needs its own decision and MySQL evidence.
- ADR-0004 remains accepted. Its payment locking participates in the tenant-first protocol; payment transitions stay inside Payment lifecycle. Do not acquire a child lock before entering a nested module that tries to acquire the tenant lock.
- Implementation order is BQ-023 (MySQL integrity suite) → BQ-067 (Payment lifecycle) → BQ-012 (this module and coordinated writers) → BQ-069 (blocked-date acceptance and regression evidence). Phase 2/G2 and the later roadmap gates remain separate; accepting this ADR does not start Phase 4 or close either implementation item.
- Tests at the module interface cover agreement across storefront/calendar/report/reschedule/walk-in, ownership validation before cleanup, rejection rollback, blocked dates, inactive fulfillment, past time, grace boundaries, multi-slot atomicity, full-group expiry, anomalies and cache invalidation/range/exclusion/time behavior. Keep HTTP tests for authorization and wiring; replace duplicated rule tests only after equivalent coverage exists.
- MySQL concurrency tests cover competing claims, claim versus closure/service changes, reschedule versus source-booking changes, and expiry/payment outcomes versus claim. SQLite results cannot establish lock correctness. BQ-025 enforces the shared authority and shrinking allowlist as callers migrate.
- This is an accepted target. Current implementation gaps and verification status remain as recorded in the domain files until implementation and evidence change them.
