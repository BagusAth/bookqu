# BookQu — Guide for Agents and Contributors

BookQu is a multi-tenant booking SaaS (Laravel 13, Blade + Alpine + Tailwind, MySQL). Each **tenant** (business) publishes **services**, opens **schedules**, and receives **bookings** that customers pay through a unified gateway (SingaPay default, Midtrans alternative). Owners work in `/owner`; customers book at `/{slug}` or a custom domain and manage bookings through access links (ADR-0006 grants); platform admins use `/admin`.

This section is the BookQu part of this file. Everything after it is the Laravel Boost block, generated by `php artisan boost:update` — never edit inside it, and never write Boost's literal opening or closing tag in this section (Boost's regex would treat it as the block start and overwrite this section).

## Before you change anything

1. Classify the task (bug fix, feature, refactor, product change, docs, ops) and pick its lane — **light** or **heavy** — see `docs/workflow.md` §2–§3.
2. Read the domain file for the area in `docs/domains/` (start at `docs/domains/README.md`). Read only the domains you touch.
3. Read `.ai/rules/index.md` and every rule file whose globs match the paths you will touch.
4. Find the requirement ID by searching `docs/requirements.md` (grep the `FR-`/`BR-` ID or keyword; do not read the whole file). No requirement ⇒ it is a product change: add an entry to `docs/product-decisions.md` for the Product Lead (through the developer) and stop.
5. Optional: if the `graphify` tool is installed and `graphify-out/graph.json` exists, query it before broad searches (`graphify query "…"`). It is a personal tool, not a requirement. Verify string-based references (routes, views, middleware aliases) with grep.

## Non-negotiable rules

1. **Tenant isolation.** No tenant may read or change another tenant's data (INV-TEN-01). Tenant context comes only from `TenantMiddleware`/`TenantContext`; never trust a tenant id from the request.
2. **User-supplied identifiers are untrusted.** Check existence, ownership, tenant and eligibility for every id, `order_id` and `booking_code`. A public identifier alone never grants access — require a customer access grant (ADR-0006).
3. **Authorization is server-side.** A hidden menu, disabled button or Alpine state is not authorization. Team roles (Pemilik, Manajer, Kasir) are decided only by `TenantPermission` (ADR-0016, once implemented); never compare role names elsewhere.
4. **Booking states** are `pending`, `paid`, `cancelled`, `completed` and `no_show` (ADR-0018); change them only through `BookingState::canTransition` (INV-BOOK-01/02).
5. **One occupancy rule.** "Slot occupied", "slot full" (capacity), unit conflicts (ADR-0017) and the pending hold (payment deadline + settlement margin, ADR-0009) live only in `App\Domain\Booking\BookingRules`; never re-implement them (INV-BOOK-03).
6. **No double booking.** Booking writes lock the tenant and schedules in a transaction, evict stale pending first, and rely on the seat index on `booking_seats` (ADR-0017) as the final guard (INV-BOOK-04/05).
7. **Payment is separate from booking.** Payment states are `pending`, `sukses`, `gagal`. Success comes only from a verified webhook or a server-side status query; repeated events must be idempotent (INV-PAY-*).
8. **Provider code stays behind** `PaymentGatewayInterface` / `PaymentGatewayManager`.
9. **Entitlement** (features, limits) is decided only by `EntitlementRules` (INV-SUB-01).
10. **Thin controllers.** Validate → call an Action → respond. Business rules live in `app/Domain`, operations in `app/Actions`.
11. **Blade and JavaScript are presentation only** — no queries, no business decisions.
12. **Never show internal errors** to users; never log passwords, secrets or tokens.
13. **Release tiers.** Do not unhide Tier 3 modules or remove Tier 2 locks without Product Lead and Tech Lead approval (ADR-0002, ADR-0011, `config/modules.php`, `OwnerSidebarNavigationTest`). Production is released only after the owner portal redesign is complete (D-018); its module, plan and role gates follow ADR-0021.
14. **A failing test is evidence.** Never edit a test just to make it pass.
15. **Smallest coherent change; no scope creep.** Record unrelated findings as a new work item. Security and data integrity beat a small diff.
16. **Existing code is evidence, not the standard.** Follow `docs/architecture.md`; do not copy known anti-patterns (see each domain's "Known gaps").

Trade-off order: security → data integrity → tenant isolation → business correctness → maintainability → testability → performance → convenience.

## Who decides

The agent asks **the developer running the session**. When the decision belongs to another role, the agent says so and stops until the developer confirms that role agreed; the PR records it.

| Change | Decided by |
|---|---|
| Implementation inside an assigned task: UI, copy, tests, internal structure, docs typos | Developer — agent may proceed |
| Domain rules (booking, availability, payment, subscription), DB schema, security, auth, `AGENTS.md`, `docs/*.md` authority docs, `.ai/rules`, ADRs, new dependencies, releasing a Tier 2/3 module | Tech Lead, **before** coding |
| Anything not in `docs/product.md` / `docs/requirements.md`, plan pricing, release to production | Product Lead, through a `D-NNN` entry in `docs/product-decisions.md`; no work item until approved |

## How work flows

1. Work happens on your own branch (`agathan`, `bagus`, or `<name>/<topic>`), synced from `integration` before you start.
2. **Light lane** (UI, copy, tests, non-authority docs, behaviour-preserving refactors): implement, run related tests, then the full suite once.
3. **Heavy lane** (domain rules, schema, security/auth, payment, tenancy, product changes): write a work item `docs/work/BQ-NNN-slug.md` from `docs/work/_TEMPLATE.md`, get the decision from the table above, then implement with full verification. A product change starts as a `D-NNN` entry in `docs/product-decisions.md`; its work item is written only after the Product Lead approves.
4. Update the domain file, requirement or ADR only where their content changed.
5. Sync from `integration` again, then open a PR into `integration` using `.github/pull_request_template.md`. A light-lane PR is audited and merged by a developer other than its author. A heavy-lane PR is audited and merged by the Tech Lead; when the Tech Lead is its author, the other developer reviews it first. Nobody merges their own PR without a review by someone else, and every merge needs the four green CI jobs. Never push to `integration` or `main` directly.

Full process, lanes, branches and definition of done: `docs/workflow.md`.
