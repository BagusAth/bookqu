# BookQu — Guide for Agents and Contributors

BookQu is a multi-tenant booking SaaS (Laravel 13, Blade + Alpine + Tailwind, MySQL). Each **tenant** (business) publishes **services**, opens **schedules**, and receives **bookings** that customers pay through a unified gateway (SingaPay default, Midtrans alternative). Owners work in `/owner`; customers book at `/{slug}` or a custom domain and manage bookings through tokenized links; platform admins use `/admin`.

This section is the BookQu part of this file. Everything after it is the Laravel Boost block, generated by `php artisan boost:update` — never edit inside it, and never write Boost's literal opening or closing tag in this section (Boost's regex would treat it as the block start and overwrite this section).

## Before you change anything

1. Classify the task (bug fix, feature, refactor, product change, docs, ops) — see `docs/workflow.md`.
2. Read the domain file for the area in `docs/domains/` (start at `docs/domains/README.md`).
3. Read `.ai/rules/index.md` and every rule file whose globs match the paths you will touch.
4. Query the knowledge graph before broad searches when `graphify-out/graph.json` exists (`graphify query "…"`, `graphify path A B`, `graphify explain X`). Verify string-based references (routes, views, middleware aliases) with grep — the graph cannot see them.
5. Find the requirement ID in `docs/requirements.md`. No requirement ⇒ it is a product change: write a work item and stop for approval.

## Non-negotiable rules

1. **Tenant isolation.** No tenant may read or change another tenant's data (INV-TEN-01). Tenant context comes only from `TenantMiddleware`/`TenantContext`; never trust a tenant id from the request.
2. **User-supplied identifiers are untrusted.** Check existence, ownership, tenant and eligibility for every id, `order_id` and `booking_code`. A public identifier alone never grants access — require a scoped token.
3. **Authorization is server-side.** A hidden menu, disabled button or Alpine state is not authorization.
4. **Booking states** are `pending`, `paid`, `cancelled`, `completed`; change them only through `BookingState::canTransition` (INV-BOOK-01/02).
5. **One occupancy rule.** "Slot occupied" and the 15-minute pending grace live only in `App\Domain\Booking\BookingRules`; never re-implement them (INV-BOOK-03).
6. **No double booking.** Booking writes lock schedules in a transaction, evict stale pending first, and rely on the `unique_active_booking_slot` index (INV-BOOK-04/05).
7. **Payment is separate from booking.** Payment states are `pending`, `sukses`, `gagal`. Success comes only from a verified webhook or a server-side status query; repeated events must be idempotent (INV-PAY-*).
8. **Provider code stays behind** `PaymentGatewayInterface` / `PaymentGatewayManager`.
9. **Entitlement** (features, limits) is decided only by `EntitlementRules` (INV-SUB-01).
10. **Thin controllers.** Validate → call an Action → respond. Business rules live in `app/Domain`, operations in `app/Actions`.
11. **Blade and JavaScript are presentation only** — no queries, no business decisions.
12. **Never show internal errors** to users; never log passwords, secrets or tokens.
13. **Release tiers.** Do not unhide Tier 3 modules or remove Tier 2 locks without lead approval (ADR-0002, `OwnerSidebarNavigationTest`).
14. **A failing test is evidence.** Never edit a test just to make it pass.
15. **Smallest coherent change; no scope creep.** Record unrelated findings as a new work item. Security and data integrity beat a small diff.
16. **Existing code is evidence, not the standard.** Follow `docs/architecture.md`; do not copy known anti-patterns (see each domain's "Known gaps").

Trade-off order: security → data integrity → tenant isolation → business correctness → maintainability → testability → performance → convenience.

## How work flows

Instructions are often abstract ("tidy up late payments"). For anything non-trivial:

1. Turn the instruction into a work item `docs/work/BQ-NNN-slug.md` from `docs/work/_TEMPLATE.md` with status `proposed`.
2. If the approval table requires it, stop and ask the lead to approve the plan.
3. Implement on a branch `bq-NNN-slug`; run the narrowest tests first, then the full suite.
4. Update the domain file, requirement or ADR only where their content changed; set the item to `done` with evidence.
5. Open a PR using `.github/pull_request_template.md`.

Full process, definition of done and conventions: `docs/workflow.md`.
